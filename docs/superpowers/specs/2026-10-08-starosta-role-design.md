# Роль старосты — дизайн

Дата: 2026-10-08

Под-проект 2 из 5 (мультигрупповость → **старосты** → соцслой →
привилегии старосты → UI-меню). Зависит от под-проекта 1 (таблицы
`groups`/`members`, `storage.list_group_members`, пикер групп с
пагинацией). Этот документ покрывает: первое назначение старосты
голосованием, смену старосты голосованием (не чаще раза в 2 недели),
прямой админ-оверрайд, и перенесённую из под-проекта 1 смену уже
закреплённой группы (тоже через аппрув). Привилегии самого старосты
(исключение участников, закрытая/открытая группа, `/notify`) и список
одногруппников — отдельные под-проекты 3/4, не входят сюда.

## Модель данных

Расширение `groups` (две новые колонки, без изменения существующих):

```
ALTER TABLE groups ADD COLUMN starosta_chat_id INTEGER REFERENCES members(chat_id);
ALTER TABLE groups ADD COLUMN last_starosta_change_at TEXT;
```

`last_starosta_change_at` — момент последнего успешного назначения/смены
(голосованием или прямым действием админа); точка отсчёта
2-недельного кулдауна на повторную смену.

Новая таблица `elections`:

```
elections(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  group_id INTEGER NOT NULL REFERENCES groups(id),
  kind TEXT NOT NULL,              -- 'initial' | 'change'
  initiated_by_chat_id INTEGER NOT NULL,
  candidate_chat_id INTEGER NOT NULL,
  status TEXT NOT NULL,            -- 'open' | 'approved' | 'cancelled'
  started_at TEXT NOT NULL,
  decided_at TEXT
)
```

На группу допускается не больше одной строки со `status='open'` —
проверяется в коде перед созданием новой (не constraint на уровне
схемы, т.к. `cancelled`/`approved`-строки той же группы легитимны и не
должны блокировать будущие голосования).

Новая таблица `election_approvals`:

```
election_approvals(
  election_id INTEGER NOT NULL REFERENCES elections(id),
  chat_id INTEGER NOT NULL,
  approved_at TEXT NOT NULL,
  UNIQUE(election_id, chat_id)
)
```

Голос «Отклонить» не пишется никуда и не блокирует голосование — решает
только количество строк в `election_approvals` (подтверждено
пользователем: отклонения не учитываются). `UNIQUE` не даёт одному
`chat_id` засчитать два голоса за одно голосование.

Новая таблица `group_change_requests` (перенесённая из под-проекта 1 —
смена уже закреплённой группы):

```
group_change_requests(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id INTEGER NOT NULL,
  from_group_id INTEGER NOT NULL REFERENCES groups(id),
  to_group_id INTEGER NOT NULL REFERENCES groups(id),
  requested_at TEXT NOT NULL,
  status TEXT NOT NULL,            -- 'pending' | 'approved' | 'rejected'
  decided_at TEXT
)
```

Не больше одной `pending`-строки на `chat_id` одновременно.

## Минимальный размер группы для голосования

И первое назначение, и смена старосты требуют **минимум 3 закреплённых
участника группы** (`storage.list_group_members(conn, group_id,
subscribed_only=False)`, кандидат + как минимум 2 потенциальных
голосующих) — иначе голосование физически не может набрать 2 аппрува.
При попытке начать голосование в меньшей группе бот отвечает «В группе
недостаточно участников для голосования, пригласите несколько человек
и попробуйте снова» и не создаёт ни `elections`, ни рассылки.

## Первое назначение старосты

- Команда `/starosta` — точка входа, показывает статус старосты
  группы вызывающего. Если `starosta_chat_id IS NULL`, нет открытого
  голосования по этой группе, и в группе ≥3 участников — показывает
  кнопку «Я староста».
- Нажатие (после проверки размера группы и отсутствия открытого
  голосования) создаёт `elections(kind='initial',
  candidate_chat_id=нажавший, initiated_by_chat_id=нажавший,
  status='open')` и рассылает **всем закреплённым за группой**
  (`subscribed_only=False`) сообщение «X предлагает себя старостой.
  Одобрить / Отклонить» с кнопками, несущими `election_id`.
- «Одобрить» → `INSERT OR IGNORE INTO election_approvals`. После
  вставки — пересчёт: при достижении 2 строк голосование закрывается
  (`status='approved'`, `decided_at=now`), `groups.starosta_chat_id` и
  `groups.last_starosta_change_at` обновляются, кандидату в личку
  уходит уведомление (см. «Уведомление нового старосты» ниже).
- «Отклонить» → только `answer()` без записи в БД.
- Пока есть открытое голосование по группе (любого `kind`) — кнопка «Я
  староста» не показывается; `/starosta` сообщает, что голосование уже
  идёт.

## Смена старосты

- Доступно **любому** участнику группы (не только старосте), когда
  `starosta_chat_id IS NOT NULL`, нет открытого голосования, в группе
  ≥3 участников, и прошло ≥14 дней с `last_starosta_change_at`.
  Нарушение кулдауна → ответ с датой, когда можно повторить попытку.
- Иначе — список одногруппников кнопками (переиспользуется пикер с
  пагинацией из под-проекта 1 при >8 участниках), включая текущего
  старосту — самовыдвижение разрешено.
- Выбор кандидата **не** запускает голосование сразу — показывается
  подтверждение: «Запустить голосование за <X> в качестве старосты? Это
  разошлётся всей группе. Подтвердить / Отмена». Только по
  «Подтвердить» создаётся `elections(kind='change', ...)` и уходит
  рассылка всем закреплённым за группой: «Начато голосование за нового
  старосту: X. Одобрить / Отклонить».
- Логика аппрувов идентична первому назначению. При успехе:
  `starosta_chat_id`/`last_starosta_change_at` обновляются; новому
  старосте уходит уведомление+гайд; **старому** старосте отдельно
  уходит уведомление, что его сменили.

## Уведомление нового старосты

Во всех трёх путях назначения (голосование initial, голосование
change, админ-оверрайд) новому старосте в личные сообщения уходит
уведомление с (а) фактом назначения, (б) указанием способа (голосование
группы / решение администратора), (в) кратким гайдом по доступным ему
командам. На этом под-проекте гайд будет минимальным (сам факт роли,
`/starosta`, участие в будущих голосованиях) — привилегии `/notify`,
исключение участников и управление открытостью группы появятся в
под-проекте 4 и дополнят текст гайда там; текст уведомления должен
жить в одном месте (одна функция форматирования), чтобы его не
редактировать в трёх местах при появлении новых привилегий.

## Админ-оверрайд

- `/set_starosta <group_id> <chat_id>` — напрямую выставляет
  `starosta_chat_id`, обновляет `last_starosta_change_at=now`, **закрывает**
  любое открытое голосование этой группы (`status='cancelled'`), и
  отправляет новому старосте то же уведомление+гайд с пометкой «назначил
  администратор».
- `/remove_starosta <group_id>` — выставляет `starosta_chat_id=NULL`,
  обновляет `last_starosta_change_at=now` (это тоже сбрасывает кулдаун —
  подтверждено пользователем), закрывает любое открытое голосование.
- `chat_id` в `/set_starosta` — сырой числовой id, как и в остальных
  админ-командах этого бота; удобный способ посмотреть список
  участников группы с никнеймами появится в под-проекте 3 (список
  одногруппников) — здесь админ ориентируется по тому, что уже видно.

## Смена группы (перенесено из под-проекта 1)

- `/change_group` — доступна любому участнику с уже закреплённой
  группой. Показывает пикер групп из под-проекта 1, исключая текущую
  группу вызывающего.
- Выбор целевой группы **не** создаёт заявку сразу — подтверждение:
  «Подать заявку на переход в группу «Y»? Подтвердить / Отмена».
  Только по «Подтвердить» создаётся `group_change_requests(status='pending')`
  — но лишь если у этого `chat_id` ещё нет другой `pending`-заявки
  (иначе ответ «у вас уже есть заявка на рассмотрении»).
- Уведомление с кнопками «Одобрить/Отклонить» уходит старосте целевой
  группы (если назначен) **и** админу параллельно; достаточно одного
  аппрува с любой стороны. Если у целевой группы старосты нет —
  уведомление уходит только админу.
- Аппрув → `chat_id` переключается на новую группу
  (`storage.upsert_member`), старая привязка перестаёт действовать,
  заявителю приходит уведомление об успехе.
- Отказ → заявка помечается `rejected`, заявитель остаётся в прежней
  группе, получает уведомление об отказе.

## `/votes` — список открытых голосований

Решает проблему «потерял исходное сообщение с кнопками Одобрить/
Отклонить» без push-напоминаний: любой участник может в любой момент
посмотреть, что сейчас голосуется в его группе, и проголосовать прямо
из этого списка — без нового механизма принятия решения.

- `/votes` — доступна **любому** закреплённому за группой участнику
  (`storage.get_member`); без закреплённой группы — подсказка про
  `/start`.
- Показывает `elections` со `status='open'` для группы вызывающего
  (на практике не больше одной — ограничение «одно открытое
  голосование на группу» из раздела «Модель данных» — но код читает
  список, а не одну строку, на случай будущих изменений этого
  инварианта). Для каждой — тип (первое назначение / смена),
  кандидат, и текущий счёт аппрувов (`COUNT(election_approvals) /2`),
  с кнопками «Одобрить»/«Отклонить», несущими **тот же** `election_id`
  и обрабатываемыми тем же хендлером, что и кнопки в исходной
  рассылке.
- Нет открытых голосований → «Нет открытых голосований.»

## Тестирование

- `elections`/`election_approvals` CRUD — юнит-тесты на подсчёт
  аппрувов, идемпотентность повторного голоса одним `chat_id`,
  срабатывание на ровно 2-м аппруве.
- Минимальный размер группы — тест на группу из 1 и 2 участников
  (блокирует), и из 3 (разрешает).
- Кулдаун 2 недели — тесты на «только что сменился» (блокирует) и
  «прошло 15 дней» (разрешает), отсчёт от `last_starosta_change_at`.
- Админ-оверрайд — тест, что он закрывает открытое голосование и
  сбрасывает кулдаун.
- `group_change_requests` — тест на единственность `pending`-заявки на
  `chat_id`, на путь «только админ» (старосты нет), на путь «староста
  или админ» (оба могут закрыть заявку одним аппрувом).
- Подтверждения («Вы уверены?») — тест, что промежуточный шаг не
  создаёт `elections`/`group_change_requests` до нажатия «Подтвердить»,
  и что «Отмена» не создаёт ничего вовсе.
- `/votes` — тест на участника без закреплённой группы (подсказка про
  `/start`), на группу без открытых голосований (пустой ответ), на
  группу с открытым голосованием (кнопка несёт тот же `election_id`,
  что и в исходной рассылке — нажатие из `/votes` засчитывается как
  обычный аппрув).

## Вне охвата этого под-проекта

- Список одногруппников как отдельная команда, видимая всем
  (под-проект 3) — используется здесь только внутренне
  (`list_group_members`) для построения списка кандидатов.
- Исключение участников, закрытая/открытая группа, `/notify`
  (под-проект 4) — в этом под-проекте только создаётся заготовка под
  расширение текста гайда новому старосте.
- Редизайн UI в инлайн-меню (под-проект 5).
