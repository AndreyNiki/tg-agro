# Привилегии старосты — дизайн

Дата: 2026-10-08

Под-проект 4 из 5 (мультигрупповость → старосты → соцслой →
**привилегии старосты** → UI-меню). Зависит от под-проекта 1
(`groups`/`members`, `group_change_requests` появляется здесь, но сам
паттерн подтверждения и аппрува — из под-проекта 2), под-проекта 2
(роль старосты, `groups.starosta_chat_id`, аппрув-флоу), и под-проекта 3
(`/classmates` — этот под-проект добавляет к нему кнопку «Исключить»
для старосты/админа). Покрывает: исключение участника, закрытую/
открытую группу с аппрувом на вступление, и `/notify`.

## Исключение участника

- В `/classmates` (под-проект 3) рядом с каждым именем, когда команду
  вызывает староста этой группы **или** глобальный админ, добавляется
  кнопка «❌ Исключить». На строке самого вызывающего кнопки нет — но
  это не единственная защита (см. ниже).
- Нажатие → подтверждение «Исключить <X> из группы? Подтвердить /
  Отмена».
- **Серверная проверка независимо от UI**: обработчик исключения
  отдельно проверяет `target_chat_id != caller_chat_id` и отказывает
  («Нельзя исключить самого себя»), даже если кнопка каким-то образом
  была показана/callback подделан — UI-скрытие кнопки — это удобство,
  не единственная защита.
- По подтверждению: `INSERT INTO group_exclusions (group_id, chat_id,
  excluded_at, excluded_by_chat_id)`, затем удаление строки `members`
  этого `chat_id` — человек полностью отвязан от группы и рассылки,
  `storage.get_member` для него снова возвращает `None`.

Новая таблица:

```
group_exclusions(
  group_id INTEGER NOT NULL REFERENCES groups(id),
  chat_id INTEGER NOT NULL,
  excluded_at TEXT NOT NULL,
  excluded_by_chat_id INTEGER NOT NULL
)
```

Без `UNIQUE` на `(group_id, chat_id)` — повторное исключение (если
человек как-то вернулся и снова исключён) добавляет новую строку, а не
конфликтует; для проверки «исключён ли» достаточно
`EXISTS(... WHERE group_id=? AND chat_id=?)`, без необходимости
различать «когда» для логики допуска (историю можно смотреть вручную
через БД при необходимости, в UI не выводится).

## Единый механизм повторного/первого вступления с аппрувом

`group_change_requests` (создана в под-проекте 2) меняется: колонка
`from_group_id` становится **nullable** (`ALTER TABLE
group_change_requests ... ` — на SQLite проще пересоздать таблицу с
нужным ограничением, см. план реализации) — `NULL` означает «вступление
впервые», не переход из другой группы.

Перед обычным мгновенным прикреплением (в `/start`-пикере без текущей
группы, и в `/change_group` с текущей группой — оба пути из
под-проектов 1 и 2) добавляется общая проверка:

```
if groups.is_closed OR EXISTS(group_exclusions WHERE group_id=target AND chat_id=caller):
    создать group_change_request(from_group_id=текущая_или_NULL, to_group_id=target, status='pending')
    уведомить старосту target (если назначен) и админа, 1 голос любого закрывает
else:
    мгновенное upsert_member, как раньше
```

Таким образом исключённый человек не может просто повторно выбрать ту
же группу в открытом виде — для него ЛЮБАЯ попытка попасть именно в
эту группу идёт через аппрув, даже если группа в целом открыта.

## Закрытая/открытая группа

`groups.is_closed BOOLEAN NOT NULL DEFAULT 0` (новая колонка).

- `/close_group [group_id]` / `/open_group [group_id]`:
  - без аргумента — резолвит группу вызывающего через
    `groups.starosta_chat_id = caller_chat_id`; если такой группы нет —
    отказ («Вы не староста ни одной группы»).
  - с аргументом `<group_id>` — доступно только глобальному админу
    (`is_admin`); старосте, указавшему `group_id` чужой группы — отказ.
- Переключение сразу меняет `is_closed`; не влияет на уже существующие
  `pending`-заявки (не отменяет и не ускоряет их).

## `/notify`

- `/notify [group_id] <текст>` — та же двойная схема аргументов, что у
  `/close_group`/`/open_group`:
  - старосте — без `group_id`, резолвит группу через
    `groups.starosta_chat_id = caller_chat_id`; если вызывающий не
    староста ни одной группы — отказ.
  - админу — обязателен `<group_id>` первым аргументом (поскольку
    `/alert` из под-проекта 1 теперь **глобальный**, рассылает всем
    пользователям бота сразу, и больше не может адресно попасть в одну
    группу — `/notify <group_id> <текст>` закрывает именно этот
    пробел для админа).
- Рассылает текст **всем закреплённым за группу**
  (`list_group_members(subscribed_only=False)`), тем же паттерном
  изоляции отказов на каждого адресата, что и везде в проекте.

## Тестирование

- `group_exclusions` — тест, что исключённый теряет строку `members`
  (отвязан от рассылки), и что повторный выбор той же группы создаёт
  `group_change_request`, а не мгновенное прикрепление.
- Саморсключение — тест, что обработчик отклоняет
  `target_chat_id == caller_chat_id` даже при напрямую собранном
  callback (не только через отсутствие кнопки в разметке).
- `is_closed` — тест, что открытая группа без записи в
  `group_exclusions` прикрепляет мгновенно, а закрытая всегда создаёт
  заявку, независимо от исключений.
- `/close_group`/`/open_group` — тест на старосту своей группы (без
  аргумента), на админа с `<group_id>` (любая группа), и на отказ
  старосте, указавшему чужой `group_id`.
- `/notify` — тест на старосту без `group_id` (рассылка всем
  закреплённым, включая отписанных от ежедневной рассылки); тест на
  админа с `<group_id>` (та же рассылка для произвольной группы); тест
  на отказ не-старосте/не-админу без `group_id`.
- Миграция `group_change_requests.from_group_id` в nullable — тест, что
  существующие строки с непустым `from_group_id` (из под-проекта 2)
  переживают пересборку таблицы без потери данных.
