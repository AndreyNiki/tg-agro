# Институты, общие PDF-файлы и кроп одной колонки на скриншоте

Дата: 2026-10-09 (ревизия после независимого ревью на противоречия)

## Контекст и цель

Сейчас каждая `group` — самостоятельная сущность с собственными
`source_page_url`/`pdf_source_url`/`send_time`/`check_interval_minutes`/
`timezone`. Любой пользователь может создать группу вручную, указав
страницу-источник; бот сам находит и валидирует колонку с её названием
в PDF (`group_commands.py`). Эта логика ещё не была выкачена в прод,
поэтому ниже схема БД **переопределяется, а не мигрируется**: таблицы
`groups`, `members`, `schedule_versions` пересоздаются с нуля при
деплое этой фичи (см. раздел 1.0). Старых данных, которые нужно было
бы сохранить, не существует.

Цель — ввести верхнеуровневую сущность **институт**:

- У института одна ссылка на страницу-каталог со списком PDF-ссылок
  (возможно, несколько групп через запятую на одну ссылку).
- Бот фоново сканирует эту страницу (периодичность настраивается),
  извлекает PDF-ссылки и разворачивает имена групп из текста ссылки
  (кейс "Б-А-301,302,303"), **не скачивая сами PDF**.
- Обычный пользователь не создаёт группы/ссылки сам — выбирает
  институт, затем готовую группу.
- Если несколько групп с подписчиками делят один PDF-файл, файл
  скачивается и парсится один раз за цикл сверки, а не по разу на
  группу.
- Сверка PDF происходит только для ссылок, у которых есть хотя бы один
  подписчик хотя бы у одной из их групп.
- Скриншот дня показывает только колонку времени + колонку нужной
  группы (расширяясь в случае "общей пары" с другими группами) плюс
  шапку с заголовками сверху.

Этот документ учитывает находки отдельного технического ревью
(проверка кода `storage.py`/`sync.py`/`scheduler.py`/`pdf_parser.py`/
`screenshot.py`/`group_links.py`/`group_commands.py`/`menu.py`/
`bot.py` на соответствие заявленным инвариантам). Решённые проблемы
отмечены пометкой **(ревью: ...)** там, где это меняет исходную схему.

## 1. Модель данных

### 1.0. Применение схемы (ревью: 1.1)

`storage.init_db` сейчас построен на `CREATE TABLE IF NOT EXISTS` +
`_ensure_column` (инкрементальный `ALTER TABLE ADD COLUMN`). SQLite не
позволяет добавить `NOT NULL`-колонку без `DEFAULT` этим способом, а
новые таблицы `groups`/`institutes`/`institute_links` вводят именно
такие колонки и меняют уникальность. Поэтому для этой фичи
`init_db` явно **дропает и пересоздаёт** `groups`, `members`,
`schedule_versions` (в этом порядке, с учётом FK) при обнаружении, что
старая схема `groups` не содержит колонку `institute_id` — то есть это
одноразовый деструктивный rebuild конкретно этих трёх таблиц, а не
аккуратная миграция. Это безопасно ровно потому, что фича ещё не в
проде (см. "Контекст").

### 1.1. Таблица `institutes`

```sql
CREATE TABLE institutes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    catalog_url TEXT NOT NULL,
    check_interval_minutes INTEGER NOT NULL,
    send_time TEXT NOT NULL,
    timezone TEXT NOT NULL,
    catalog_refresh_interval_minutes INTEGER NOT NULL,
    last_catalog_sync_at TEXT,
    created_at TEXT NOT NULL
)
```

`check_interval_minutes`/`send_time`/`timezone` общие для всех
ссылок/групп института. `catalog_refresh_interval_minutes` управляет
периодичностью фонового пересканирования каталога (по умолчанию "раз
в неделю", настраивается администратором).

Удаление института не реализуется этой фичей (вне скоупа запроса);
`institute_links.institute_id` и `groups.institute_id` — `ON DELETE
RESTRICT`, то есть институт с живыми группами удалить нельзя на
уровне БД — явный guard от случайной потери подписчиков (ревью: 1.5).

### 1.2. Таблица `institute_links`

```sql
CREATE TABLE institute_links (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    institute_id INTEGER NOT NULL REFERENCES institutes(id) ON DELETE RESTRICT,
    pdf_url TEXT NOT NULL,
    group_names_json TEXT NOT NULL,
    raw_label TEXT NOT NULL,
    is_stale INTEGER NOT NULL DEFAULT 0,
    last_seen_at TEXT NOT NULL,
    created_at TEXT NOT NULL,
    UNIQUE(institute_id, pdf_url)
)
```

`pdf_url` — финальный абсолютный адрес `.pdf` (страница каталога
содержит прямые `<a href="*.pdf">`, см. `group_links.resolve_pdf_link`,
который уже вытаскивает такие ссылки по тому же паттерну).
`group_names_json` — развёрнутый (через `expand_group_names`, раздел
2) список имён групп, актуальный на момент последнего успешного
сопоставления; `raw_label` хранится только для отладки/логов, **не**
как ключ (ревью: 2.1 — текст ссылки слишком волатилен, чтобы на нём
строить идентичность строки).

**Ключ идентичности ссылки — двухфазный** (ревью: 1.2, 2.1, 3.3):

1. Основной ключ — `(institute_id, pdf_url)`. Если на новом скане
   встретился `pdf_url`, который институт уже знает — это та же
   ссылка, просто обновляем `group_names_json`/`raw_label`/
   `last_seen_at`/`is_stale=0`.
2. Если `pdf_url` новый (не встречался у этого института) —
   сравниваем развёрнутый список имён групп с группами **каждой уже
   известной, но не подтверждённой в этом скане** ссылки. Если
   множества имён совпадают **точно** — это смена адреса файла той же
   логической ссылки: обновляем `pdf_url` существующей строки
   (`id` и, следовательно, привязка групп, не меняются).
3. Если ни один из двух матчей не сработал — создаём новую строку
   `institute_links` и новые/обновлённые `groups`.

Если в рамках **одного** скана два разных `(pdf_url, raw_label)`
элемента каталога дают одинаковый `pdf_url` — они считаются одной
ссылкой: их развёрнутые списки имён объединяются в одну строку перед
upsert'ом (ревью: 1.2 — иначе один и тот же файл скачивался бы дважды
только из-за дублирования подписи на странице).

### 1.3. Устаревание ссылок (ревью: 1.3, 3.4)

Строки `institute_links`, не подтверждённые ни одним из двух матчей на
очередном скане, получают `is_stale = 1` (а не удаляются — история
`raw_label` остаётся для диагностики). `sync_institute_link` **не
делает сетевых попыток** для ссылок с `is_stale = 1` — это и устраняет
бесконечный цикл 404-попыток, и устраняет "404-stampede"
(раздел 3.4): при массовом сбое сайта все ссылки института помечаются
устаревшими за один проход переcканирования, а не порождают по
отдельному пересканированию на каждую упавшую ссылку.

Первая же ссылка, помечённая `is_stale=1` при наличии у неё хотя бы
одной группы с подписчиком, шлёт администратору **один** алерт
("ссылка института N пропала из каталога, подписчиков затронуто: K") —
без повторов на каждый последующий цикл. Группы такой ссылки не
закрываются и не удаляются; `/schedule` продолжает отдавать последнюю
успешно засинканную версию.

### 1.4. Изменения в `groups`

Убираем: `source_page_url`, `pdf_source_url`, `send_time`,
`check_interval_minutes`, `timezone` — выводятся через
`institute_id`/`institute_link_id`.

Добавляем: `institute_id INTEGER NOT NULL REFERENCES institutes(id) ON DELETE RESTRICT`,
`institute_link_id INTEGER NOT NULL REFERENCES institute_links(id) ON DELETE RESTRICT`.

Уникальность меняется с `name UNIQUE` на `UNIQUE(institute_id, name)`
(ревью: 1.6 — `storage.get_group_by_name(conn, name)` меняет
сигнатуру на `get_group_by_name(conn, institute_id, name)`; все
вызывающие места обновляются).

Остальные колонки (`starosta_chat_id`, `last_starosta_change_at`,
`is_closed`, `last_sync_failed_at`, `created_at`) не меняются.

Группы создаются и обновляются **только** сканированием каталога
(upsert по `(institute_id, name)`). Правило при конфликте (ревью:
2.3) — если в рамках **одного** скана имя группы встречается в
развёрнутых списках двух разных ссылок: если группа уже существует и
её текущий `institute_link_id` — один из этих двух кандидатов,
привязка **не трогается** (группа остаётся там же); если ни один не
совпадает (включая случай новой группы) — выбирается первая ссылка по
порядку на странице, и событие логируется как предупреждение
(без алерта администратору — это редкий, не аварийный случай).

Группы, не встреченные в развёрнутых списках ни одной живой
(`is_stale=0`) ссылки института при скане — не закрываются и не
удаляются автоматически; расхождение логируется. Если впоследствии
окажется, что единственная ссылка, к которой они привязаны, стала
`is_stale=1` — применяется алерт из 1.3.

### 1.5. Валидация имени группы против реального PDF (ревью: 2.4, 2.5, 2.7)

Сканирование каталога **не скачивает PDF** (явное требование) и не
может проверить, что развёрнутое имя группы действительно совпадает с
текстом в шапке таблицы (регистр/дефисы в тексте ссылки и в PDF могут
отличаться). Поэтому группа, полученная из каталога, считается
**непроверенной** до первой попытки подписки: добавляем
`groups.is_verified INTEGER NOT NULL DEFAULT 0`.

Первый пользователь, пытающийся подписаться на непроверенную группу
(раздел 4, пикер), триггерит одноразовую проверку: скачать
`institute_link.pdf_url`, вызвать `find_header_column_index` (не
`find_group_column_index`!) на полный список имён этой ссылки —
поиск обязан быть ограничен зоной шапки таблицы (раздел 5.1), иначе
имя, упомянутое только в тексте занятия другой группы, пройдёт
валидацию, но затем будет постоянно проваливать реальную синхронизацию,
которая тоже ищет только в шапке — и для каждого имени, которое **не нашлось** — пометить
соответствующую группу `is_verified = -1` ("не найдена", скрывается из
пикера и логируется с алертом администратору) вместо `1`.
Пользователю, пытавшемуся подписаться на невалидную группу, возвращается
"Группа временно недоступна, администратор уведомлён." Остальные
(найденные) группы той же ссылки получают `is_verified = 1`.

Это одновременно: (а) решает проблему ложной группы без скачивания
лишних PDF (валидация происходит только по реальному запросу
пользователя, не на весь каталог сразу); (б) даёт естественную точку
для немедленного первого sync (раздел 4.2).

Лёгкий текстовый фильтр-эвристика (regex на форму "Буква(-ы)-Буква(-ы)-Цифры",
настраиваемый по институту) отсеивает явный мусор (приказы, методички)
**на этапе разворачивания имён**, до создания строки `groups` — не
заменяет валидацию по PDF, а снижает число заведомо мусорных записей в
пикере до первой подписки.

### 1.6. `members`, `schedule_versions`

Не меняются структурно. `schedule_versions.group_id` остаётся
обязательной ссылкой на группу; каждая группа хранит свою активную
версию и свой кэш-файл отдельно (раздел 3 объясняет, почему это
сознательно не шарится на уровне БД, хотя сетевой фетч дедуплицирован).

## 2. Сканирование каталога института

Новая функция в `group_links.py` (переиспользует `_PDF_LINK_RE`,
`_TAG_RE`):

```python
def list_pdf_links(html: str, base_url: str) -> list[tuple[str, str]]:
    """Возвращает [(pdf_url, raw_label), ...] для каждой <a href="*.pdf">
    на странице, без фильтрации по конкретной группе."""
```

Нормализация перед любым сравнением текста (ревью: 2.1): `raw_label`
прогоняется через `strip()`, сжатие множественных пробелов/`\xa0` в
один пробел, но **не** через `casefold` — регистр в развёрнутых именах
групп значим и должен совпасть с PDF при валидации (раздел 1.5).

Разворачивание имён — операциональное правило (ревью: 2.6):

```python
_TRAILING_DIGITS = re.compile(r"\d+$")

def expand_group_names(raw_label: str) -> list[str]:
    """Разбивает raw_label по запятым (пробелы вокруг запятой
    игнорируются). Фрагмент, состоящий только из цифр, дополняется
    префиксом предыдущего полного имени в этой же строке — префикс
    определяется как "предыдущее полное имя с отрезанными конечными
    цифрами" (re.sub(_TRAILING_DIGITS, "", prev)):
    "Б-А-301,302,303" -> ["Б-А-301", "Б-А-302", "Б-А-303"].
    Фрагмент с буквами — самостоятельное полное имя:
    "Б-Эв-101, Б-Мв-101" -> ["Б-Эв-101", "Б-Мв-101"].
    Если первый фрагмент строки — чисто число (нет предыдущего имени),
    строка целиком считается невалидной и пропускается с предупреждением
    в лог — такая метка не похожа на формат, под который
    калибровалось это правило (см. ограничение ниже)."""
```

**Известное ограничение** (ревью: 2.5): правило калибровано под
формат "Префикс-Цифры[,Цифры...]" и под явный список полных имён через
запятую. Реальные метки произвольной формы (например, "1 курс БЭ, БМ
оз" — пример из текущего докстрайна `resolve_pdf_link`) могут не
содержать ни одного валидного по regex-фильтру (раздел 1.5) кандидата
и тогда просто не породят ни одной группы — это осознанно безопасное
поведение (лучше пропустить ссылку, чем создать мусорные группы), но
значит, что для институтов с нестандартным форматом подписей
администратору нужен способ посмотреть, какие ссылки каталога **не**
дали ни одной группы (новая admin-команда `/institute_links <id>`,
раздел 4, показывает все `raw_label` института с числом групп,
включая 0).

`refresh_institute_catalog(conn, institute)`:

1. Фетчит `institute.catalog_url`.
2. `entries = list_pdf_links(html, institute.catalog_url)`; группирует
   по `pdf_url` (дубли подписи на один файл — см. 1.2) и для каждого
   уникального `pdf_url` считает объединённый `expand_group_names`
   по всем его подписям, прогоняет через текстовый фильтр (1.5).
3. Для каждого `(pdf_url, group_names)` — двухфазный upsert
   `institute_links` (раздел 1.2), затем upsert `groups` по
   `(institute_id, name)` с правилом конфликта (раздел 1.4).
4. Все `institute_links`, не подтверждённые в этом скане — `is_stale=1`
   (раздел 1.3), с единичным алертом там, где есть подписчики.
5. `institutes.last_catalog_sync_at = now()`. Если `len(entries) == 0`
   — **ничего не апдейтится** (транзакция не коммитится дальше шага
   чтения), только лог + алерт администратору "каталог института N
   вернул 0 ссылок" (ревью: 2.8 — защита от 200 OK с пустой/битой
   страницей, которая иначе обнулила бы все привязки).

Вызывается вручную (`/refresh_institute_links <id>`, переименована из
`/refresh_institute`, чтобы не путать с PDF-сверкой — см. раздел 4) и
фоново по `catalog_refresh_interval_minutes`.

404 на `pdf_url` во время PDF-сверки (раздел 3) триггерит
`refresh_institute_catalog` для всего института **не чаще одного раза
за цикл сверки** (ревью: 3.3, 3.4) — если скан каталога уже
выполнялся в рамках этого запуска планового job'а (отслеживается
флагом на время одного прогона `institute_check_*`, не персистентным),
повторные 404 от других ссылок того же прогона не триггерят новый
скан, а просто используют уже обновлённые данные или помечаются
`is_stale` на следующем плановом скане.

`resolve_group_pdf_source`/`resolve_pdf_link`-использование в
пользовательском создании групп и сам `group_commands.py` удаляются
целиком (раздел 4). `resolve_pdf_link` как функция остаётся в
`group_links.py`, но используется только `list_pdf_links`
опосредованно (общий регэксп), не вызывается напрямую по имени группы.

## 3. Пайплайн сверки (sync) — дедупликация скачивания и парсинга

### 3.1. Дедупликация парсинга, не только фетча (ревью: 3.1 — было прямым противоречием)

`pdf_parser.py` уже разделён на I/O-слой (`extract_raw_rows`, один
вызов на файл) и чистую интерпретацию (`find_group_column_index` +
`build_schedule`, вызываются на каждое имя). Новая функция явно
использует этот разрез, вместо того чтобы вызывать `parse_schedule`
(которое делает `extract_raw_rows` заново) на каждую группу:

```python
def parse_schedules_for_groups(
    source: str, group_names: list[str]
) -> dict[str, Schedule | None]:
    """Один extract_raw_rows(source). Для каждого имени —
    find_group_column_index + build_schedule на УЖЕ извлечённых rows.
    Имя, для которого колонка не найдена, получает None (не исключение) —
    используется и штатной сверкой, и одноразовой валидацией (1.5)."""
```

Это и есть фактическая дедупликация самой дорогой части (сетевой фетч
+ pdfplumber-разбор таблицы) — не только скачивания байтов.

### 3.2. `sync_institute_link` — асинхронная, блокирующий код в `to_thread` (ревью: 3.2)

```python
async def sync_institute_link(
    conn, institute_link, pdf_cache_dir: str, notify: Notifier
) -> list[SyncResult]:
```

1. `groups = storage.list_groups_for_link(conn, institute_link.id)`;
   `active_groups = [g for g in groups if storage.list_group_members(conn, g.id, subscribed_only=False)]`
   (ревью: 3.6 — **не** `subscribed_only=True`: отписавшийся, но
   закреплённый пользователь должен продолжать получать актуальные
   данные по `/schedule`, таким образом синхронизация не привязана к
   статусу рассылки). Если `active_groups` пуст или `institute_link.is_stale`
   — выход без сетевых запросов.
2. Скачивание + `parse_schedules_for_groups(tmp_path, [g.name for g in active_groups])`
   выполняются внутри `asyncio.to_thread(...)` одним вызовом — то же
   обоснование, что сейчас в `check_and_apply_diff` (комментарий про
   TOCTOU и блокирующий I/O), просто на уровне ссылки, а не группы.
3. При устойчивой ошибке скачивания — фоллбэк на пересканирование
   каталога (раздел 2), затем повтор с обновлённым `institute_link.pdf_url`,
   **перечитанным из БД через group.institute_link_id** (а не из
   переданного в функцию объекта — после двухфазного upsert'а из
   раздела 1.2 именно БД знает актуальный адрес; ревью: 3.3).
4. Временный файл с байтами PDF удаляется в `finally` один раз — после
   обработки всех групп, не на каждой итерации (ревью: 3.9).
5. Для каждой группы из `active_groups`, чей `Schedule` не `None`:
   `compute_diff` против активной версии этой группы; при изменении —
   `_write_cache` пишет копию в
   `Path(pdf_cache_dir) / f"link_{institute_link.id}" / safe_group_name / f"{timestamp}.pdf"`,
   где `safe_group_name` строится явно из санитайзенных сегментов, а
   не передачей `"12/Б-А-301"` одной строкой в текущий regex-санитайзер
   (который заменил бы `/` на `_` и дал бы `12_Б-А-301`, не
   вложенную папку — ревью: 3.5). Далее — `insert_new_version`,
   рассылка (`subscribed_only=True` здесь — это именно про доставку
   уведомления, см. п.1) с тем же try/except-изоляция-на-подписчика,
   что и сейчас.
6. Решение **скачать/распарсить один раз, но писать по копии на
   группу** остаётся простым компромиссом раздела 3.1 исходной версии
   — не вводит рефкаунт shared-файла и не ломает существующий
   `test_sync_deletes_superseded_cache_file_on_change`.

### 3.3. `last_sync_failed_at` (ревью: 3.7)

- Сбой скачивания `institute_link.pdf_url` (после retry и одного
  catalog-рефреша) — `last_sync_failed_at` ставится **всем**
  `active_groups` этой ссылки (общая причина).
- Успешное скачивание, но `find_group_column_index` не нашла колонку
  конкретной группы (функция вернула `None` для этого имени) —
  `last_sync_failed_at` ставится **только** этой группе; остальные
  группы той же ссылки, для которых колонка нашлась, обрабатываются
  штатно и их `last_sync_failed_at` сбрасывается.

### 3.4. Блокировки (ревью: 3.8)

`group_locks` (сейчас словарь `asyncio.Lock` на `group_id`) заменяется
на словарь на `institute_link_id`. Плановый job (раздел 4) и ручной
`/refresh <group_id>` (раздел 4.1, восстановлен) резолвят группу в её
`institute_link_id` и берут один и тот же lock — одна ссылка не
синкается параллельно из двух источников, но разные ссылки одного
института синкаются независимо.

## 4. Планировщик, admin-команды, меню, пользовательский выбор

### 4.1. Планировщик — job'ы на уровне ссылки, не института (ревью: 4.4 — пересмотр исходного решения)

Исходная версия этого раздела предлагала один job на **институт**,
итерирующий все его ссылки последовательно — ревью справедливо
указало, что это легко выходит за `check_interval_minutes` на
институтах с десятками ссылок и ломает расписание рассылки без
`max_instances`/`misfire_grace_time`. Вместо этого:

- `link_check_{institute_link_id}` — `IntervalTrigger(minutes=institute.check_interval_minutes)`
  (институт резолвится через `institute_link.institute_id`), вызывает
  `sync_institute_link` для одной ссылки. Ссылки без активных групп
  пропускаются внутри самой функции (раздел 3.2, п.1) — дешёвая
  no-op, а не тяжёлый цикл.
- `link_daily_send_{institute_link_id}` — `CronTrigger` из
  `institute.send_time`/`timezone`, рассылает скриншот дня подписчикам
  этой ссылки.
- `institute_catalog_refresh_{institute_id}` — один job на институт
  (это легковесный одиночный фетч страницы, не требует разбиения по
  ссылкам), `IntervalTrigger(minutes=institute.catalog_refresh_interval_minutes)`.

Число job'ов — порядка O(ссылок), то есть сопоставимо с текущим
O(групп) (ссылок обычно меньше или равно числу групп), без риска
"расползания" одного job'а на час.

`bot_data["reschedule_institute_link_jobs"](institute_link_id)` и
`bot_data["reschedule_institute_jobs"](institute_id)` — новые хуки,
аналог текущего `reschedule_group_jobs`, вызываются после
`refresh_institute_catalog` (новые/обновлённые ссылки должны получить
свою пару job'ов — ревью: 4.3) и после `/add_institute`/`/set_institute_*`.

### 4.2. Немедленная первая сверка при первой подписке (ревью: 4.2)

Раньше `startup_sync_{group_id}` (`DateTrigger(run_date=now)`) и вызов
`reschedule_group_jobs` из `group_commands.py` гарантировали, что после
создания группы `/schedule` не ждёт `check_interval_minutes`. В новой
модели группы создаёт сканер (без подписчика — без смысла синкать), а
подписка происходит через пикер. Решение: валидация группы при первой
подписке (раздел 1.5) **на успехе** сразу вызывает
`await sync_institute_link(...)` для её ссылки (вне расписания, в
контексте обработчика подписки) — тот же эффект, что раньше давал
`startup_sync`, но привязанный к реальному моменту появления первого
подписчика, а не к созданию группы.

### 4.3. Admin-команды

## 5. Скриншот — колонка времени + колонка группы (+ шапка)

### 5.1. Геометрия строки заголовка — не "первое совпадение где угодно" (ревью: 5.3)

`find_group_column_index` сейчас сканирует **все** строки таблицы и
возвращает первое вхождение `group_name` как подстроки в тексте любой
ячейки — если имя группы случайно встретилось раньше в тексте урока
другой группы ("совм. с Б-А-301"), `header_idx` указал бы на строку
тела, а не на шапку. Для этой фичи это критично, т.к. на `header_idx`
строится видимая геометрия шапки скриншота. Решение: поиск для целей
геометрии шапки ограничивается строками **до первой `row.day_marker ==
True`** — это и есть зона заголовка таблицы по построению (после
первого маркера дня идут только данные уроков). Та же граница
используется, чтобы гарантировать, что индекс колонки, найденный в
этой зоне, корректен и для всего тела (структура таблицы — одна и та
же колонка на весь документ).

```python
def find_header_column_index(rows: list[RawRow], group_name: str) -> tuple[int, int]:
    """Как find_group_column_index, но поиск ограничен rows[:first_day_marker_index]."""
```

### 5.2. Геометрия колонок на `DaySchedule` (без изменений по сути)

`DaySchedule` получает `time_col_x0/x1`, `group_col_x0/x1` —
min/max-агрегация (`touch_bounds`, тот же приём, что уже для `y0/y1`)
по `x0/x1` **фактически использованной ячейки** в каждой строке дня
(своей или merge-ячейки слева). Строки, где ни своей, ни merge-ячейки
не нашлось (`if not found: continue` в `build_schedule`), не влияют на
x-агрегацию — но их `y0/y1` всё равно учтены в `touch_bounds`, вызванной
раньше в цикле; это сознательное несовпадение множеств строк для x и
для y (ревью: 5.7), и именно поэтому день без единого найденного
урока у группы может иметь валидные `y0/y1`, но `group_col_x0/x1 is
None` — такой день просто не шлёт фото (текстовое сообщение, как и
сейчас при отсутствии уроков).

### 5.3. Известное ограничение в дни с "общей парой" (ревью: 5.1 — переформулировка, не исправление)

Эвристика мержа в `build_schedule` опознаёт растянутую ячейку условием
"правый край ячейки достигает правого края **всей таблицы**"
(`other.x1 >= table_x1 - epsilon`) — это существующее, документированное
в CLAUDE.md и покрытое тестами поведение, которое эта фича не меняет.
Следствие: ширина скриншота в день с "общей парой" будет равна ровно
тому, что эта эвристика считает "общим" — от начала найденной
растянутой ячейки до **правого края всей таблицы**, а не до соседней
группы, если та физически не является последней колонкой. Если
институтский PDF кладёт "общую пару" не в последние колонки,
скриншот такого дня покажет больше групп, чем реально участвует в
паре. Это не новая ошибка этой фичи, а точное отражение существующей
приближённой эвристики — исправление самой эвристики мержа не входит
в объём этой фичи (она тестами зафиксирована отдельно,
`test_merged_cell_spanning_to_table_edge_applies_to_target_group`) и
будет отдельной задачей, если окажется проблемой на практике.

### 5.4. Шапка — та же ширина, что и тело (ревью: 5.2 — исправление)

`Schedule` получает только `header_y0`/`header_y1` (из
`rows[header_idx].y0/y1`, `header_idx` — результат
`find_header_column_index`) — **без** отдельных `header_group_col_x0/x1`/
`header_time_col_x0/x1`. Шапка на финальном изображении вырезается
**тем же** x-диапазоном, что и тело конкретного дня
(`day.time_col_x0/x1`, `day.group_col_x0/x1`), только по `y`-диапазону
`header_y0/y1`. Это гарантирует одинаковую ширину шапки и тела для
любого дня, включая дни с "общей парой" (раздел 5.3) — шапка в такой
день покажет заголовки всех групп, попавших в расширенный диапазон,
что согласовано с телом.

### 5.5. Сборка изображения, пересечение диапазонов (ревью: 5.5)

`render_day_image`:

1. Если `day.group_col_x0/x1 is None` (нет геометрии — день без
   найденного урока у группы, раздел 5.2) — текстовое сообщение без
   фото, как и сейчас для "нет уроков".
2. Иначе: если `time_col_x1 + padding >= day.group_col_x0 - padding`
   (диапазоны смежны/пересекаются — ожидаемо в "общей паре", если
   группа стоит прямо после колонки времени) — один непрерывный кроп
   от `time_col_x0` до `day.group_col_x1`, без склейки. Иначе — два
   отдельных пикмапа (время, группа), склеенные горизонтально.
3. Шапка строится тем же правилом (п.1-2, но по `header_y0/y1`) и
   склеивается с телом вертикально.
4. x-границы берутся непосредственно из `Cell.x0/x1`, которые
   pdfplumber репортит по границам реальных линий таблицы — отдельного
   "снаппинга" к сетке не требуется (ревью: 5.6), т.к. это и есть
   источник геометрии, а не произвольные координаты.

### 5.6. Обратная совместимость — не нужна (ревью: 5.8, 5.9 — удалено)

Первая версия документа вводила fallback на старое поведение для
"старых закэшированных JSON без новых полей". Это противоречило
собственному пункту "без миграции данных" (раздел 1.0 — `groups`/
`schedule_versions` пересоздаются, старых payload'ов физически не
будет). Fallback убран; `DaySchedule.time_col_x0` и соседние поля —
обязательные (`float`, не `float | None`) в итоговой модели.

### 5.7. Алерт администратору — только на broadcast-путях (ревью: 5.10)

Обработка ошибок сборки изображения различается по пути:

- `scheduler.daily_send_job` / рассылка после `sync_institute_link`
  (broadcast) — любое исключение при рендере: подписчику уходит
  текстовое сообщение без фото, администратору — **один** алерт на
  весь прогон рассылки (не на каждого подписчика), с текстом ошибки,
  группой и днём.
- `bot.day_callback` (интерактивный `/schedule`) — как и сейчас,
  только логирование, без алерта админу: иначе один повреждённый
  кэш-файл даст администратору сообщение на каждое нажатие дня каждым
  пользователем.

## Итог

Институт — верхнеуровневая сущность с каталогом PDF-ссылок,
периодичностью сверки и временем отправки. Каталог сканируется фоново
без скачивания PDF и разворачивает имена групп из текста ссылок, с
двухфазным (по `pdf_url`, затем по набору имён) upsert'ом ссылки и
явным устареванием (`is_stale`) вместо удаления. Группы создаются
автоматически, но считаются непроверенными до первой попытки подписки
— тогда же происходит одноразовая валидация против реального PDF и
немедленный первый sync. Сверка расписания скачивает и **парсит**
общий PDF-файл один раз за цикл (не только скачивает) независимо от
числа подписанных на него групп, выполняется только при наличии хотя
бы одной закреплённой (не обязательно подписанной на рассылку) группы,
и работает на уровне ссылки (не института) в планировщике, чтобы не
накапливать задержку. Скриншот дня показывает колонку времени и
колонку нужной группы с согласованной по ширине шапкой сверху;
расширение в "общую пару" — точное отражение существующей
мерж-эвристики, не новая логика. Ошибки сборки изображения не
блокируют отправку текста; алерт администратору шлётся только с
broadcast-путей и один раз на прогон.
